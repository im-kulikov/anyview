# Журнал решений (ADR)

Формат записи: контекст — решение — последствия. Статус: **принято** (уже в коде) или **предложено** (записано до фазы 2, в коде не реализовано).

## Принято

### ADR-01. Единая лента для главной и `/anime`
Один ключ Query, `pageSize` 30, `refetchOnMount: false`, дедуп по `id`. Главная — один сетевой запрос, `/anime` уже в кэше. Живая лента даёт дубли между страницами, поэтому дедуп при склейке и в React-ключах. SPEC §5.1, §5.2.

### ADR-02. URL как состояние
`?episode=` и `?q=` меняются через `replace` + `preventScrollReset`; поле поиска живёт в `Layout` и не перемонтируется. Так «Назад» работает предсказуемо, а прокрутка не прыгает. SPEC §4, §5.6.

### ADR-03. Поиск и CORS-404
API отвечает 404 без CORS на пустой результат, браузер видит `TypeError`. Правило с `shortcut:`: базы не перебираем, пустой результат — если сеть онлайн и база уже отвечала. Устранение первопричины — прокси с CORS или свой сервер. API_CONTRACT §5.1.

### ADR-04. iOS: синхронный `play()` и фокус
Один `<video>` без `src` до первого нажатия, `preload="none"`, источники грузятся заранее; поиск в основном чанке, фокус — синхронно в касании. SPEC §5.5, §5.6.

### ADR-05. Поля ввода ≥ 16 px, зум не отключаем
Иначе iOS приближает страницу при фокусе. Правило повторено в SPEC §9, DESIGN §6 и CLAUDE.md намеренно; источник правды — SPEC §9.

### ADR-06. Хранение прогресса
Ключи `anyview:v1:*` (progress, history, favorites, recentSearches, prefs), одна запись истории на тайтл, порог «просмотрено» 90 %, снимок `TitleSummary`, лимиты 500/50/200/8. SPEC §7.

### ADR-07. Свой `IntersectionObserver` в `Cover`
Нативный `loading="lazy"` загружает картинки с запасом ≈ 1250 px и забивает канал; своя подгрузка в 200 px. SPEC §8.

### ADR-08. Прокручивается окно, а не контейнер
Нужно для `ScrollRestoration`. Приём макета с внутренним скроллом не переносим. SPEC §4, §5.

### ADR-09. GitHub Pages и копии `index.html` вместо hash-роутера
`404.html` даёт код 404 на `/title/*`, приложение при этом открывается. Критерий пересмотра — собственный домен или хостинг с SPA-fallback и заголовками (CSP). SPEC §10.

### ADR-18. Подсказки загрузки генерируются при сборке
`preconnect` и `preload` первой страницы ленты были записаны в `index.html` с жёстким хостом и `quantity=30`: при смене `VITE_ANIMEVOST_BASES`, `FEED_PAGE_SIZE` или `VITE_PROVIDER` preload превращался в лишний запрос (≈ 106 КБ) на чужой домен. Теперь `config/htmlPlugin.ts` (Vite `transformIndexHtml`, без зависимостей) строит их из тех же `parseBases`/`lastPath`/`FEED_PAGE_SIZE`, которыми пользуется адаптер; `og:image` получает абсолютный адрес из `VITE_SITE_URL`. Последствия: `index.html` не содержит адресов API; тест `config/htmlPlugin.test.ts` держит их согласованными. Закрывает CODE-26, ARCH-19.

### ADR-19. Шрифт Exo 2 с собственного хоста
Google Fonts давали внешний CSS, два preconnect, inline `onload` (мешал строгому CSP) и единую точку отказа (доступность из РФ). Три подмножества переменного woff2 (cyrillic 19 КБ, latin 41 КБ, latin-ext 31 КБ; скачивается только нужное по `unicode-range`) лежат в `public/fonts`, `@font-face` — в `styles/fonts.css`. Лицензия шрифта — SIL OFL, раздача разрешена. Lighthouse не изменился (74–76 до и после): выигрыш в устойчивости и возможности CSP. Preload шрифта не делаем: он конкурирует за канал с JS и лентой до первой отрисовки.

### ADR-20. CSP через `<meta>`
Только в сборке (dev-сервер Vite использует inline-скрипты). `default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'` (inline нужен атрибутам `style`, например `aspect-ratio` в `Cover`), `img-src 'self' https: data:`, `media-src https: blob:` (видео и картинки приходят с нескольких CDN animevost, список хостов заранее неизвестен), `font-src 'self'`, `connect-src 'self'` + origin баз API (из `VITE_ANIMEVOST_BASES`, при `VITE_PROVIDER=anyview` — из `VITE_API_BASE`), `object-src 'none'`, `base-uri 'self'`, `form-action 'none'`. `frame-ancestors` и report-only через `<meta>` не работают; при уходе с GitHub Pages перенести CSP в заголовки. Проверено в браузере: картинки, шрифты, запросы к API и загрузка mp4 проходят, нарушений нет. Закрывает ARCH-18 (CSP).

### ADR-21. Снимок ленты для повторного визита (stale-while-revalidate)
Холодный старт: HTML → JS → `/last` (106 КБ, ≈ 1.3 с) → обложка. Для вернувшегося пользователя первая страница ленты (≈ 13 КБ после маппинга) хранится в `anyview:v1:feed`, при старте кладётся в кэш Query как устаревшая (`updatedAt: 0`), запрос к API идёт как раньше и заменяет данные; ошибка сети оставляет снимок на экране. Безопасность: элементы проходят ту же проверку формы, что и остальное хранилище, возраст ≤ 7 суток, «вечно» показанных старых данных нет (каждая загрузка начинается с перепроверки). «Главная — один сетевой запрос» сохраняется. **Отклонено**: снимок ленты, вшитый в сборку (cron-деплой + предзагруженная обложка в HTML). Прототип дал Lighthouse 79–83 вместо 75 (только вместе с отложенной загрузкой остальных обложек), но показывает всем новым посетителям устаревшую ленту, делает сборку зависимой от чужого API и множит деплои. Пересмотреть при отсутствии прокси/своего сервера (фаза 2).

### ADR-22. Отмена общих запросов по числу подписчиков
`title`, `episodes`, `sources` разделяют один `/info` и один `/playlist` на тайтл, поэтому отмена сигнала одной страницы не могла оборвать запрос (и не обрывала: `fetch` шёл без сигнала, SPEC §6 нарушался). Теперь у общей загрузки свой `AbortController` и счётчик подписчиков (`memo` в `providers/animevost/index.ts`): `abort()` — когда отписался последний; недогруженная запись удаляется из кэша, завершённая остаётся (поздняя отмена кэш не стирает). Тесты в `provider.test.ts`. Закрывает CODE-17.

### ADR-23. Поиск: контрольный запрос вместо эвристики «база уже отвечала»
Браузер не отличает 404 без CORS («ничего не нашли») от обрыва сети. Прежнее правило давало ложную ошибку на холодном старте `/search?q=…` (CODE-21). Теперь при `TypeError` идёт один запрос `/last?page=1&quantity=1`: ответил — значит, пусто. Остаётся `shortcut:` до прокси с CORS или своего сервера. Альтернатива «ждать префетч ленты» отвергнута: связывает поиск с лентой и ломается при её сбое. API_CONTRACT §5.1. Закрывает CODE-21, ARCH-10 (в части различения; перебор баз для поиска не добавлен: поиск — POST, повтор на второй базе удвоил бы нагрузку при каждом пустом запросе).

### ADR-24. Строгий `https()`
`https(url, base?)` возвращает `undefined` для любых схем кроме `http`/`https` и нечитаемых адресов, разрешает относительные адреса от `base`. Список разрешённых хостов не вводим: CDN animevost меняются, ложный отказ ломает картинки и видео, а защиту от чужих хостов даёт CSP (ADR-20). Закрывает CODE-24, ARCH-18 (https).

### ADR-25. Освежение ленты и отчёты об ошибках
Лента не менялась до перезагрузки вкладки (CODE-35). Полный refetch бесконечного запроса перезагрузит все страницы (до ≈ 12 МБ) и нарушит «возврат на `/anime` не перезагружает загруженные страницы», поэтому при возврате на вкладку с данными старше 15 мин (`3 × staleTime`) запрашивается только первая страница и подставляется на место первой (`api/refresh.ts`). Дубли на стыке убирает `dedupe`. Навигация по-прежнему без запросов. Рядом: `lib/report.ts` и перехватчики (`app/diagnostics.ts`) — первый шаг ADR-16 без приёмника; `vite:preloadError` перезагружает страницу один раз за минуту (ARCH-17). Закрывает CODE-35, ARCH-12 (освежение, `select` вынесен из рендера), ARCH-17.

### ADR-26. Версия схемы хранилища и вытеснение при квоте
Ключи остаются `anyview:v1:*`, формат не менялся. Добавлены общий ключ `anyview:schema` и `migrate()` с таблицей `MIGRATIONS` (шаг n → n+1), чтобы смена формата не требовала нового префикса и не бросала данные: сначала миграция, потом чтение. Правила: нет записи = v1; упавшая миграция не повышает версию (чтение защищено поэлементной валидацией); версия выше известной не понижается. При `QuotaExceededError` вытесняется только кэш (`anyview:v1:feed`), пользовательские ключи не трогаем; не помогло — режим памяти (CODE-06). Атомарность progress/history и обновление снимков избранного (ARCH-23) не делались: потеря между двумя `set` и устаревший снимок не ломают экраны. Закрывает ARCH-04 (миграции), ARCH-05 (квота).

### ADR-27. Синхронизация: модель данных и слияние
Что синхронизируется: прогресс, история, избранное. **prefs (качество, громкость, автопереход) и недавние запросы — нет**: они зависят от устройства (громкость на телефоне и компьютере разная), а их потеря ничего не стоит. Состояние (`LocalData` в `lib/storage.ts`) сливается чистой функцией `mergeData` (`src/sync/merge.ts`), без DOM и сети:
- **progress** — по `episodeId` побеждает больший `updatedAt`; лимит 500 (вытесняются старые).
- **history** — одна запись на тайтл, самая свежая; лимит 50. Затем сверка с прогрессом: запись старше досмотренной (≥ 90 %) позже серии того же тайтла устарела и отбрасывается. Так правило «досмотрено → следующая серия или удаление» переживает слияние: устройство, где досмотрели, уже создало запись на следующей серии (она свежее) либо удалило свою, и старая копия с другого устройства не воскресает.
- **favorites** — `TitleSummary[]` не хранит времени, поэтому рядом лежит `anyview:v1:favoritesMeta`: `{[id]: {at, del?}}`, где `at` — момент добавления или удаления, `del` — «надгробие». Побеждает более позднее действие, при равенстве удаление сильнее (удалённое не воскресает). Лимиты: 200 живых, 300 «надгробий» (самые свежие). Порядок — по `at`, новые сверху.
- Ключи `anyview:v1:*` остаются, формат существующих не менялся. Схема 1 → 2 (`MIGRATIONS[1]`): уже добавленным тайтлам выставляются метки `at` = 1, 2, … (старые, порядок сохраняется). Без метки (откат деплоя и повторный вход) избранное считается добавленным с `at` = 0.
- Равные `updatedAt` разрешаются сравнением канонического JSON (ключи отсортированы), а не порядком аргументов. Свойства, проверенные тестами на 300 случайных состояний: **коммутативность** и **идемпотентность** (в том числе `merge(a, merge(a, b)) = merge(a, b)`), слияние с пустым не теряет данных. **Ассоциативности нет**: отбрасывание устаревшей записи истории необратимо, и порядок трёх слияний может дать разный результат в редком случае «досмотрел, затем сбросил и пересмотрел»; сходимость обеспечивается идемпотентностью (каждое устройство каждый раз сливает облако с локальным).
- Часы устройств считаются примерно верными (метки — `Date.now()`): расхождение в минуты проигрывает только в пределах этих минут, расхождение в дни может отдать победу не тому устройству. Принято, серверное время в метках не используем (нужен был бы второй документ и лишние запросы).
- `resetProgress` («С начала») теперь обновляет `updatedAt`: иначе сброс проигрывал бы старой записи другого устройства.
- **Атомарность (ARCH-23)**: `batch()` откладывает уведомления подписчиков до конца группы записей; `saveProgress`, `resetProgress`, `toggleFavorite` и применение слитого состояния (`writeLocal`) меняют связанные хранилища одним согласованным обновлением для `useSyncExternalStore`. Запись в `localStorage` по-прежнему идёт по ключам по очереди (транзакций у него нет), но экраны промежуточного состояния не видят. Закрывает ARCH-23 в части progress/history/избранного; обновление снимков избранного при открытии тайтла по-прежнему не делается.
- **Размер**: правила Firestore требуют `data.size() < 200000`. Для облака состояние обрезается (`fitForCloud`) до 190 000 байт UTF-8: пачками по десятой части выбрасываются самые старые записи прогресса и истории, если их нет — «надгробия», затем избранное. Локальные данные не обрезаются; тест на 200 длинных избранных и 500 серий.

### ADR-28. Синхронизация: Firebase Auth + Firestore, вход через Google Identity Services
Заказчик выбрал вариант «вошёл один раз — и всё работает». **Зависимость `firebase`** (вне списка CLAUDE.md): писать самим OAuth, обновление токенов и REST к Firestore дороже и небезопаснее. Используются только `firebase/app`, `firebase/auth` и `firebase/firestore/lite` (REST, без realtime-соединения и офлайн-кэша IndexedDB); всё — в `src/sync/firebase.ts` и грузится динамическим `import()` **только** после «Включить синхронизацию» или при выполненном входе (флаг `anyview:sync` в `localStorage`, старт через 2 с после первой отрисовки). Чанк `firebase` ≈ 57 КБ gzip, `engine` ≈ 3 КБ; стартовый бандл вырос на ≈ 0.5 КБ (128.2 КБ, бюджет 150). Правило ESLint запрещает статический импорт `src/sync/**` и `firebase*` из остального кода (исключение — ленивый экран `src/features/sync`).
- **Вход.** Не `signInWithRedirect` и не `signInWithPopup`: при `authDomain` ≠ `github.io` их ломает partitioned storage в Safari и Chrome. Вместо этого Google Identity Services (`accounts.google.com/gsi/client`, кнопка `renderButton`, `auto_select`), ID-токен из callback → `signInWithCredential(GoogleAuthProvider.credential(token))`. `initializeAuth` без `popupRedirectResolver`, персистентность IndexedDB → `localStorage`. Токен нигде не хранится и не логируется. Типы GIS — локальный `src/sync/gis.d.ts`.
- **Модель документа** `users/{uid} = {schema: 1, updatedAt: serverTimestamp(), data: строка JSON}` — ровно по опубликованным правилам (`firestore.rules`). Содержимое — `LocalData` (ADR-27). Правила разрешают запись только владельцу и ограничивают `data` 200 000 символов; для запаса режем до 190 000 байт.
- **Конфликты.** `runTransaction` из `firestore/lite`: чтение документа → `mergeData(локальное, облачное)` → запись, если строка изменилась. Если другое устройство записало документ между чтением и записью, Firestore повторяет функцию — слияние пересчитывается по свежему облаку. Локальное облаком вслепую не затирается: после транзакции слитое снова сливается с актуальным локальным (пользователь мог смотреть видео во время обмена). Облачный документ новее известной схемы — отказ, не перезапись.
- **Расписание** (`schedule.ts`, `engine.ts`): при входе и при старте для вошедшего; при возврате на вкладку не чаще раза в 60 с; отправка через 5 с после последнего изменения локальных хранилищ, но не позже 30 с с первого (при непрерывном просмотре позиция пишется каждые ~5 с и без этого отправка откладывалась бы бесконечно); `visibilitychange: hidden` и `pagehide` — best-effort отправка (запрос может не успеть); сетевые ошибки — повтор через 5, 10, 20 … с (до 5 мин, 6 попыток), затем ждём «Повторить»; офлайн ничего не делаем, по событию `online` синхронизируем.
- **Удаление данных из облака**: `deleteDoc`. Опубликованные заказчиком правила одним `allow write` с проверкой `request.resource.data` отказывают при удалении (`request.resource` равен `null`), поэтому в `firestore.rules` `delete` вынесен отдельно, а код при `permission-denied` перезаписывает документ пустым состоянием. После удаления выполняется выход на этом устройстве (иначе следующая синхронизация вернула бы данные).
- **CSP** (ADR-20) расширяется, только если в сборке задан Firebase: `script-src https://accounts.google.com/gsi/client` (скрипт GIS), `style-src https://accounts.google.com/gsi/style` (стиль кнопки), `frame-src https://accounts.google.com/gsi/` (iframe кнопки), `connect-src https://accounts.google.com/gsi/` + `identitytoolkit.googleapis.com` (вход) + `securetoken.googleapis.com` (обновление токена) + `firestore.googleapis.com` (документ). Wildcard `*.googleapis.com` и `*.firebaseapp.com` не нужны: iframe `authDomain` не используется. `img-src https:` уже есть. Не проверено в живой сессии (см. docs/SYNC.md).
- **Конфигурация** — `.env.production` в репозитории (`VITE_FIREBASE_*`, `VITE_GOOGLE_CLIENT_ID`): это публичные значения, файл работает и в CI, и локально для `npm run build`, без переменных репозитория GitHub. В dev и тестах (режимы `development`, `test`) файл не читается — синхронизация выключена, страница показывает «Синхронизация недоступна».
- **Отклонено**: Firebase `getAuth` с popup/redirect (см. выше); полный `firebase/firestore` (realtime и кэш — лишние ≈ 100+ КБ и фоновые соединения); собственный сервер (противоречит «своего сервера нет»); синхронизация prefs (ADR-27).

### ADR-29. Связи тайтлов (сезоны и «Похожие») в адаптере
Заказчик хочет навигацию по сезонам; у animevost нет понятия франшизы, своего сервера пока нет (решение заказчика: позже это сделает сервер). **Решение:** `ContentProvider.related(id) → RelatedTitles {seasons, similar}` (API_CONTRACT §2–§4); адаптер определяет связи по одному `POST /search` на франшизу (запрос — «голова» названия, иначе база; кэш по нормализованному запросу, общий промис), правила — API_CONTRACT §5.3, код — `providers/animevost/related.ts`. Русский маркер сезона авторитетен, номер из оригинала не берём (цифры в конце — часть названия); поиск API идёт по подстроке, поэтому результаты фильтруются по границе слова; поиск по оригинальному названию добавлял связи лишь в ~1 % случаев — не делаем. **Последствия:** на 881 тайтле из 336 сохранённых поисков ложных сезонов нет, «Похожих» нет у ~57 % тайтлов; не связываются франшизы с разными русскими названиями (Наруто/Боруто), возможен разрыв номеров (Pokémon), дубль номера (ремейк) уходит в «Похожие». Сбой `related` не ломает страницу (интерфейс игнорирует ошибку) и не кэшируется как «связей нет»: адаптер бросает `ApiError`, Query не сохраняет успех (исправлено после первой версии, где сбой давал пустой результат на 60 минут). Исследование: `docs/research/related-titles.md`. **План замены:** сервер отдаёт `GET /titles/{id}/related` по собственным данным (shikimori/MAL-связи), адаптер animevost и `related.ts` удаляются; контракт и UI не меняются.

### ADR-30. Сведения о тайтле из Shikimori и AniList в адаптере

Заказчик хочет жанры, первоисточник и автора, возрастной рейтинг, студию, героев и сейю; у animevost их нет, сервера нет. **Решение:** `ContentProvider.details(id) → TitleDetails` (API_CONTRACT §2–§5); адаптер ищет тайтл в Shikimori по оригинальному названию и году, берёт карточку и по MAL id запрашивает AniList (`providers/animevost/details.ts`). Только строгое совпадение имени: лучше пусто, чем чужой тайтл. CSP `connect-src` дополнен `shikimori.io` и `graphql.anilist.co` (CORS у обоих `*`). Страница не ждёт: блоки появляются, когда данные пришли; ошибка скрывает их молча и не кэшируется. **Последствия:** найдено 101 из 120 (84 %), ложных пар нет; зависимость от чужих публичных API без SLA (лимиты 90/мин, Shikimori сменил домен `.one`→`.io`); у ходовых китайских тайтлов нет сейю. Исследование: `docs/research/title-details.md`. **План замены:** сервер сопоставляет один раз и отдаёт `GET /titles/{id}/details`.

### ADR-31. Списки просмотра и раздел «Моё»

Один флаг «избранное» не отвечает на «что я смотрю, что отложил, что в планах»; избранное и история были видны только на главной. Владелец попросил оценку улучшений, продуктовый критик отнёс списки к первой волне (`docs/research/ux-improvements.md`). **Решение:** отдельное хранилище `statuses` (`watching/planned/done/hold/dropped`, `null` = «надгробие») рядом с избранным, а не вместо него — миграция избранного в статусы рискованнее выгоды; слияние по `at` (новее побеждает, при равенстве канонический JSON), лимиты 300 живых и 300 «надгробий»; страница `/library` с вкладками; выбор статуса — нативный `<select>` на странице тайтла; «Новая серия» считается сравнением снимка в истории/«Смотрю» с лентой обновлений (снимок «Смотрю» обновляется при просмотре без изменения `at`). Облачный документ — `schema: 2`: старые клиенты на нём получают `SchemaError` и не затирают статусы. В нижней панели телефона «Сериалы» и «Фильмы» заменены на «Моё» и «Скоро» (`/series`, ссылка на `/movies`; прямые ссылки сохранены). **Последствия:** история без возможности удаления записи (нужны «надгробия» истории, отложено); «Новая серия» зависит от ленты и не видит тайтлы, выпавшие из неё; автодобавления в «Смотрю» при просмотре нет. **План замены:** сервер хранит списки и считает «новое» сам.

### ADR-32. E2E-smoke в реальном Chromium вместо jsdom; проверка до и после публикации

Релиз волны 3 сломал главную у пользователей с историей просмотра из ≥ 2 записей (переменная использовалась до объявления внутри компонента). Типы, lint, 191 unit-тест и сборка были зелёными, потому что ни одна проверка не открывала экран с непустыми данными localStorage; проверка после деплоя была `curl -f` на статику. Три критика (код, архитектура, тестирование) сошлись на одном решении. **Решение:** `@playwright/test` (dev) запускает собранный `dist/` через `vite preview` в Chromium, сеть полностью подменена (`e2e/mockApi.ts`: фикстура ленты `e2e/fixtures/last.json`, Shikimori/AniList недоступны, любой незнакомый хост = ошибка теста), данные пользователя задаются наборами `e2e/seeds.ts` (пусто, 2 и 50 записей истории, полные списки, схема до версионирования, мусор во всех ключах, схема новее известной, неверные типы полей). `e2e/smoke.e2e.ts`: каждый маршрут × наборы × телефон/десктоп — экран отрисовался, экрана ошибки нет, в консоли нет ошибок, нет запросов к чужим хостам; плюс проверки содержимого («Продолжить» при истории ≥ 2, вкладки «Моё», сбой ленты). Тест проверен на регрессии: на коде релиза с ошибкой он падает. В CI шаг идёт до публикации (красный e2e = нет артефакта Pages = нет деплоя); после деплоя тот же набор (поднабор) запускается против боевого URL с подменой сети: красный шаг — тревога, откат вручную. **Не jsdom:** он нарушал бы правило проекта, требовал моков платформы (`matchMedia`, `IntersectionObserver`, `HTMLMediaElement`, router) и не видит сборку, CSP, чанки и `base`. **Последствия:** +1,1 мин и установка Chromium (~40 с) в CI; новая dev-зависимость; фикстуры могут разойтись с реальным API (контрактные тесты на записанных ответах и ночная сверка — отложены); WebKit/iOS Safari по-прежнему только вручную.

### ADR-33. Отчёт о проблеме одной кнопкой и расшифровка стека

Диагностика сбоя требовала, чтобы пользователь открыл консоль браузера и пересказал её: так искали ошибку главной после волны 3. **Решение:** `lib/bugReport.ts` собирает текст отчёта (версия сборки = sha коммита из `VITE_BUILD_SHA`, страница, окружение, ошибка со стеком, последние ошибки вкладки из кольцевого буфера в `report()`, форма данных `anyview:*` без содержимого; содержимое — только по галочке, с лимитами); компонент `BugReport` копирует его в буфер (запасной путь — выделенный текст) и стоит на экране ошибки и на странице `/diagnostics`. Сборка выпускает hidden sourcemaps (карты лежат рядом с чанками, браузер их не грузит), `scripts/decode-stack.mjs` превращает `index-….js:23:23579` в `src/…:21:59`. **Последствия:** карты публикуются вместе с сайтом (+≈1 МБ в артефакте Pages, исходники и так открыты); отчёт не содержит токенов (читаются только `anyview:*`); отправки на сервер нет — пользователь сам вставляет отчёт в чат (приёмник по-прежнему вне MVP, ADR-16); ошибки сети и чужого API попадают в отчёт, только если прошли через `report()`.

### ADR-34. «Моё» внутри «Аккаунта»; сезоны в избранном одной карточкой

ADR-31 вынес «Моё» отдельной вкладкой и заменил «Сериалы» и «Фильмы» в нижней панели телефона. Владелец: «Моё» выглядит как часть «Аккаунта», лишние вкладки раздувают навигацию; на десктопе для этого есть место. **Решение:** «Моё» стало секцией страницы «Аккаунт» (`/sync`, сверху; ниже — синхронизация), в нижней панели телефона вернулись «Сериалы» и «Фильмы», в шапке десктопа «Моё» убрано (там кнопка «Аккаунт»), `/library` перенаправляет на `/sync` с теми же `?tab=`. **Избранное и сезоны.** Идея владельца: показывать только последний сезон, к остальным вести оттуда. Оценка: плюсы — нет россыпи сезонов, избранное читается как «аниме», а не «серии аниме», переход между сезонами уже есть (блок «Сезоны», ADR-29); риски — избранное осознанный выбор пользователя (спрятанный сезон не «потерян», но не виден), ложные склейки (ремейки, разные названия), несогласованность со статусами и историей, которые по сезонам. **Принято:** группировка только при показе (данные и синхронизация не меняются), в избранном и в ленте «Избранное» на главной; бейдж «N сезона» и подсказка, что открывается последний; последний — по номеру из имеющихся в избранном (о более новых сезонах без сети неизвестно — они на странице тайтла); не группируем при повторе номера сезона, фильмы/OVA/спэшлы отдельно; статусы и «Продолжить» остаются по сезонам. Франшиза определяется новым методом `ContentProvider.franchiseOf` (локально и синхронно; для animevost — база названия и маркер сезона, ограничения те же, что у ADR-29: «Наруто»/«Боруто» не склеиваются), чтобы слой интерфейса не знал о правилах animevost, а сервер подставил свой идентификатор франшизы. **Последствия:** `S.nav.library` и вкладка удалены; число в «Избранное» — число карточек, не записей; снять сердце у скрытого сезона можно только на его странице. Ссылка `library.html` в деплое остаётся для старых ссылок.

### ADR-35. Фаззинг: unit-свойства (fast-check) и случайные порчи данных на экранах

Фиксированные примеры проверяют то, что мы догадались проверить; сбой волны 3 проходил именно потому, что никто не придумал историю из двух записей. Нужен поиск проблем, которых «не видно здесь и сейчас». **Решение:** `fast-check` (dev) — генерация входов и автоматическое сжатие найденного сбоя до минимального примера с сидом. Два уровня. (1) Unit (`*.fuzz.test.ts`, в `npm test`, 150 прогонов на свойство; глубоко — `FC_RUNS=20000`): граница с чужим API (произвольные типы в любых полях ответа animevost → карточка и страница не бросают, картинки только https, id серий уникальны, `classifyRelated` согласован), разбор строк (идемпотентность нормализации, не бросают), данные пользователя (произвольный JSON и целенаправленная порча листа «злым» значением в любом ключе `anyview:*` → чтение не бросает, повторный разбор не меняет данные, форматы/статусы/числа пригодны для отрисовки), слияние (коммутативность и идемпотентность), чистая логика экранов (фильтр, группировка сезонов, форматирование). (2) E2E (`e2e/fuzz.e2e.ts`, сценарии: 2–8 порч данных + мусорный элемент ленты + телефон/десктоп, обход ключевых экранов; критерий — нет ошибки страницы и экрана «Что-то пошло не так»): в PR 4 сценария с фиксированным сидом, ночью (`.github/workflows/fuzz.yml`) — unit на 20 000 прогонов и 100 сценариев с случайным сидом, сид печатается. **Что нашёл при внедрении:** `type: "__proto__"` (словарь без hasOwn → формат становился объектом прототипа; так же `SOURCE`/`AGE`/`MONTHS`/`ORDINALS` и подписи форматов из хранилища), `year`/`rating` объектом с `toString: 0` (`Number()` бросает), `std`/`hd` плейлиста не строкой (`RegExp.exec`), формат/статус снимка из хранилища не из известных значений. **Уроки:** `fc.nat()` смещён к малым значениям — выбор листа дерева должен быть `fc.noBias`, иначе порча не доходит до глубоких полей; e2e-фаззер широкий, но медленный (≈5 с на сценарий) и редко попадает в конкретное поле, остро ловят unit-свойства — поэтому инварианты отрисовки проверяются на уровне чтения данных. **Последствия:** +≈20 с в CI (PR), ночной прогон ≈ 15–25 мин; красный ночной прогон — реальная находка (сид и пример в логе), а не флейк; добавлять свойство на каждую новую границу данных (новый ключ хранилища, новое поле чужого API).

## Предложено (до фазы 2)

- **ADR-10. Идентификаторы и миграция данных.** `av-*` персистятся без namespace; при смене провайдера данные пользователя осиротеют. Нужны правила legacy-id, `externalIds`, миграция `localStorage`.
- **ADR-11. Выбор провайдера и включение типов.** `VITE_PROVIDER` → фабрика; `catalog()` как единственный источник «что включено»; `comingSoon` как декоратор. Сейчас провайдер собран вручную в `src/api/index.ts`.
- **ADR-12. Владелец кэша.** TanStack Query — единственный кэш; в адаптере только дедуп in-flight; TTL по типам данных. Политика ретраев (не ретраить 4xx) и TTL адаптера уже сделаны; кэш сырых элементов в адаптере остаётся.
- **ADR-13. Архитектура плеера.** Редьюсер состояния, движки по `Stream.kind` (hls/dash/iframe), выбор источника по озвучке/студии/высоте, `expiresAt`.
- **ADR-14. Модель серий для сериалов.** `(season, number)` как ключ порядка, `absoluteNumber` для аниме, стабильность `Episode.id`.
- **ADR-15. Безопасность на статическом хостинге.** CSP через `<meta>` и самохостинг шрифтов сделаны (ADR-19, ADR-20); осталось: строгий `https()`, критерий ухода с GitHub Pages.
- **ADR-16. Наблюдаемость.** `report()` и перехватчики есть (ADR-25); осталось: приёмник ошибок и что считать инцидентом (рост `parse`-ошибок, 5xx).
- **ADR-17. Хранилище: остаток.** Версии, миграции, валидация элементов и квота сделаны (ADR-26); атомарность progress/history сделана (ADR-27); осталось: обновление снимков избранного при открытии тайтла, ключи с namespace провайдера (ARCH-01: сервер принимает legacy `av-*`, API_CONTRACT).
